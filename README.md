# WaveTime

WaveTime — веб-сервис сети бассейнов для записи и бронирования тренировок/сеансов плавания.

## 1. Назначение проекта
Сервис предназначен для:
- онлайн-записи клиентов на сеансы плавания;
- управления бронированиями и подтверждениями со стороны администрации;
- приема онлайн-оплат;
- хранения и обработки данных по расписанию, записям и посещаемости.

Минимальная цель MVP: обеспечить полностью рабочий цикл
`регистрация -> выбор слота -> бронь -> оплата -> подтверждение -> админ-контроль`.

## 2. Роли пользователей

### 2.1 Клиент
- Регистрация и авторизация.
- Просмотр расписания.
- Выбор филиала, даты и времени.
- Создание и отмена бронирования.
- Оплата бронирования.
- Просмотр истории/статусов в личном кабинете.

### 2.2 Администратор
- Просмотр всех записей и оплат.
- Подтверждение, отмена, перенос брони.
- Управление слотами и их вместимостью.
- Отметка факта посещения.
- Аудит действий в системе.

## 3. Функциональные требования (MVP)

### 3.1 Расписание
- Сетка сеансов: ежедневно с `07:00` до `23:00`.
- Длительность одного слота: `60 минут`.
- Отображение доступности слотов по местам.

### 3.2 Выбор и бронирование
- Выбор дня недели и конкретного времени.
- Выбор филиала (бассейна).
- Проверка вместимости в момент бронирования.
- Временный резерв места на время оплаты (например, 15 минут).

### 3.3 Авторизация и личный кабинет
- Поля профиля: `ФИО`, `телефон`, `email`.
- Регистрация по email/телефону и паролю.
- Вход/выход, обновление токена доступа.
- Просмотр активных и прошедших броней.

### 3.4 Оплата
- Инициация платежа из бронирования.
- Получение статуса платежа по webhook от провайдера.
- Статусы платежа: `pending`, `paid`, `failed`, `refunded`, `cancelled`.

### 3.5 Администрирование
- Просмотр и фильтрация записей.
- Изменение статуса бронирования.
- Корректировка параметров слота (включая вместимость/доступность).
- Логирование действий администратора.

### 3.6 Уведомления
- Отправка email/SMS по ключевым событиям:
  - создание брони;
  - подтверждение оплаты;
  - отмена/перенос.

## 4. Нефункциональные требования
- Работа с часовыми поясами филиалов.
- Безопасность:
  - хранение паролей только в виде hash;
  - JWT access/refresh;
  - базовая защита от повторной обработки webhook (идемпотентность).
- Производительность:
  - загрузка расписания на неделю при типовой нагрузке менее 2 секунд.
- Надежность:
  - транзакционная защита от овербукинга.
- Наблюдаемость:
  - логирование ошибок и ключевых бизнес-событий.

## 5. Бизнес-правила
- Пользователь не может забронировать один и тот же слот дважды.
- Количество бронирований в слоте не может превышать вместимость.
- Неоплаченная бронь автоматически истекает по `reserved_until`.
- Клиентская отмена возможна только до дедлайна (настраиваемое правило, например 2 часа до начала).
- Администратор может выполнять ручные корректировки с фиксацией причины.

## 6. Минимально достаточная модель данных (PostgreSQL, Fat DB)

Основные сущности:
- `users` — пользователи и роли;
- `pools` — филиалы бассейнов;
- `training_types` — типы тренировок/сеансов;
- `slots` — конкретные временные интервалы и их вместимость;
- `bookings` — бронирования пользователей;
- `payments` — платежные операции;
- `attendance` — факт посещения;
- `admin_actions` — аудит действий администратора;
- `notification_queue` — очередь уведомлений.

Ключевые ограничения и механики:
- уникальность брони: `UNIQUE (user_id, slot_id)`;
- проверка вместимости и длительности слота;
- индексация для быстрого поиска по расписанию и статусам;
- триггеры `updated_at`;
- триггерная синхронизация `slots.booked_count` при изменении `bookings`;
- запрет овербукинга на уровне БД.

## 7. План backend (Go, REST API)

### 7.1 Технологический минимум
- Go
- HTTP framework: `chi` или `gin`
- PostgreSQL driver: `pgx`
- Миграции: `golang-migrate`
- Авторизация: JWT access + refresh

### 7.2 Минимальный API
- Auth:
  - `POST /auth/register`
  - `POST /auth/login`
  - `POST /auth/refresh`
  - `POST /auth/logout`
- Profile:
  - `GET /me`
  - `PATCH /me`
- Schedule:
  - `GET /pools`
  - `GET /schedule?pool_id&date_from&date_to`
- Bookings:
  - `POST /bookings`
  - `GET /bookings/my`
  - `DELETE /bookings/{id}`
- Payments:
  - `POST /payments/init`
  - `POST /payments/webhook`
- Admin:
  - `GET /admin/bookings`
  - `PATCH /admin/bookings/{id}`
  - `POST /admin/slots`
  - `PATCH /admin/slots/{id}`

## 8. План frontend (Vue.js)

### 8.1 Технологический минимум
- Vue 3 + Vite
- Pinia
- Vue Router
- Axios

### 8.2 Страницы MVP
- Вход/регистрация.
- Расписание (день/неделя, фильтры, выбор слота).
- Подтверждение брони и переход к оплате.
- Личный кабинет (профиль, текущие и прошлые записи).
- Админ-интерфейс (записи, слоты, статусы).

### 8.3 UX-минимум
- Ясные статусы: свободно/мало мест/нет мест.
- Таймер резерва брони на этапе оплаты.
- Понятные сообщения об успешных/неуспешных операциях.

## 9. Этапы реализации MVP
1. Уточнение ТЗ, финализация ERD, миграции БД.
2. Базовый backend: auth + расписание + брони.
3. Интеграция оплаты и webhook.
4. Базовый frontend пользовательского кабинета.
5. Админ-функции и аудит.
6. Тестирование, стабилизация, деплой.
